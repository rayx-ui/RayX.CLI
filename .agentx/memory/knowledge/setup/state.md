# Setup State

## Purpose And Usage

Read before changing what `rayx setup` installs, how it decides what is missing, what `rayx doctor` reports, or how `setup --wsl` drives WSL.

## Current Technical Shape

App commands use the engine through `src/app/prereqs.rs` (`Step::prompts`, `Step::optional_for_builds`, `environment_for`). The Chromium probe finds `playwright-core` in pnpm's store (`node_modules/.pnpm/playwright-core@*`), not only at the top level. All requirement sets, `doctor`, `setup --wsl` and `wsl status`/`compact` are implemented in `src/setup/`, `src/doctor.rs`, `src/setup/wsl.rs` and `src/wsl.rs` (epic `rayx-cli-foundation`, design decisions `d-setup-plan` and `d-wsl`). `src/setup/mod.rs` is the engine: `Set`, `PlanEnv`, `Step { probe, install }`, `Action` (`Run`, `AddToPath`, `WriteFile`, `RemoveFile`, `Custom`), `plan`, `check`, `execute`, `render_plan` and `run_plan`; `machine.rs` is the `Machine` observation trait (`SystemMachine`, `FakeMachine`). `--check` prints each step's status and exact commands and exits 1 when anything is missing; a run executes only missing steps, re-probes after each, stops at the first failure and ends with "Nothing to do" the second time. Apt steps batch into one `apt-get update` plus one `apt-get install` (`-y` only with `--yes`).

- `linux.rs`: Ubuntu/Debian (and `ID_LIKE` derivatives, also in WSL) apt list from SETUP-2, probed with `dpkg-query` (status `i` in the second `Status-Abbrev` character); other distributions fail with a message naming Ubuntu and Debian.
- `rust.rs`: rustup (`curl | sh` with `--default-toolchain none --no-modify-path`), the project's `rust-toolchain.toml` toolchain installed from the project directory (else `stable` plus `rustup default stable`), `~/.cargo/bin` on the user PATH. On Windows the toolchain must carry the native triple.
- `windows.rs`: winget (missing winget stops with the App Installer instruction), Build Tools (VCTools, plus the ARM64 component on ARM64; an existing Visual Studio is modified with its `setup.exe`), VC++ redistributables per architecture, LLVM and its PATH entry, the newest Windows SDK `fxc.exe` directory for the host architecture (fallback to the other) on PATH, rustup from `rustup-init.exe` for the native triple, `rustup set default-host`.
- `macos.rs`: Command Line Tools through the on-demand marker, the newest `softwareupdate` label and `sudo softwareupdate --install` (fallback `xcode-select --install` and wait; `Cx::with_clt_marker` redirects the marker for tests), Homebrew through the official script (a `sudo -v` first under `--yes`, `/opt/homebrew/bin` on PATH on Apple silicon), then the Rust steps. One step table feeds `setup`, `setup --check` and `doctor`. It replaces gpux's `LINUX-WSL.md` sections 2–4, the gpux skill's prerequisite references and `install-windows-prereqs.ps1`, and RayX xtask's `setup-android` and `setup-wasm`.

- `web.rs`: the pinned nightly with `rust-src` and the wasm32 target, the wasm32 target on the project's toolchain, `wasm-bindgen-cli` at the locked version (`cargo install ... --force --locked`), and Homebrew's LLVM on macOS (Apple's clang has no wasm32 backend; Linux and Windows get clang from the base set).
- `test_tools.rs`: Node at the pinned major (NodeSource on Ubuntu, `OpenJS.NodeJS.LTS`, Homebrew `node@<major>`), pnpm through `corepack enable --install-directory ~/.local/bin`, xvfb/xdotool and the Chromium libraries (`t64` names on Ubuntu 24.04 and Debian 13), and the project's Playwright package (`tools-node` or `[workspace.metadata.rayx] tools-node`): `pnpm install --frozen-lockfile --prefer-offline` (redone when `pnpm-lock.yaml` is newer than `node_modules/.modules.yaml`) and `pnpm exec playwright install chromium` into the per-user cache with `PLAYWRIGHT_BROWSERS_PATH` set explicitly. `find_tool` resolves node/corepack/pnpm on PATH (skipping `/mnt/*` under WSL) and in the install locations, and `with_node_path` prefixes the command's PATH with Node's directory because the corepack shim starts `node` by name.
- `android.rs`: JDK 21 + `JAVA_HOME` (user variable), Android Studio (skipped under WSL and without a desktop), SDK found in xtask order, command-line tools downloaded when missing, one `sdkmanager --install` for the missing packages (the pinned NDK is required; another installed NDK does not stand in for it, an `ANDROID_NDK_HOME`/`ROOT`/`NDK_HOME` directory does; system image at the platform pin for the host ABI), default AVD `rayx-<platform>-<abi>` (only that AVD satisfies the check, other AVDs may point at an image that is not installed; emulator log lines ignored). The app build uses the pinned NDK, installs it when missing and falls back to the newest installed one with a warning only when the install fails; it also resolves the pinned JDK for Gradle, runs `gradlew` through `sh` on Unix, and starts the emulator on the `rayx-` AVD first with `-gpu host`, then the AVD's own GPU setting, acceleration (kvm group, elevated `dism` for the Windows Hypervisor Platform with a restart notice), `cargo-ndk` and the Android Rust targets. `.bat` tools start by full path.
- `ios.rs` (macOS only): Xcode versions read from `version.plist` (no `xcodebuild` needed), `xcodes`/`mas`, `xcode-select --switch` to the pin-matching app, license (`accept` only with `--yes`), first launch, Simulator runtime, XcodeGen, iOS targets.
- `gpu.rs`: adapter detection (DXGI through the `windows` crate, `lspci` + `vulkaninfo`, `powershell.exe` under WSL, `system_profiler`) and one driver step. Checked 2026-10-08: winget has no NVIDIA, AMD or Qualcomm display driver package, so Windows Update is used (UsoClient scan + optional-updates page); Intel adds `Intel.IntelDriverAndSupportAssistant`; Ubuntu NVIDIA uses `ubuntu-drivers install`; Mesa covers AMD/Intel; virtual adapters are informational.
- `doctor.rs`: requirements as present/missing/wrong-version with `found` versions and exact fixes, GPU adapters, `hardwareAdapter` (needs a working driver), `interactiveDesktop` (console session / DISPLAY / Aqua), WSL findings and, from Windows, the `ext4.vhdx` sizes (`src/wsl.rs`). Exit 0 whenever the host could be inspected.

- `setup/wsl.rs` (`setup --wsl [--clone [<dir>]]`, Windows only): requires `wsl --version` to print a dotted version (the label is localized), installs `Ubuntu-<pin>` (`setup::guest::wsl_distribution`) when absent and stops for the first user, installs the Linux `rayx` of the same version with that release's own installer (`releases/download/v<version>/rayx-cli-installer.sh | sh` inside the distribution, so it lives in `~/.rayx/bin/rayx` with a receipt and `rayx self update` works there; an architecture without a Linux release fails before any download), or copies `RAYX_WSL_BINARY` to `~/.rayx/bin/rayx` (no receipt), runs `rayx setup --gpu` on Windows first for `--gpu`/`--all`, then `wsl -d Ubuntu-24.04 --exec bash -lc 'rayx setup <flags>'` in the same console. `--clone` clones only the current checkout through `/mnt/<drive>` (absolute or `~` target only), fetches an existing clone, and records it in `~/.config/rayx/clones` inside the guest (`wsl status` and `compact --clean` also read the legacy `wsl-clones`). The Linux `rayx` install, clone and inner setup live in `src/setup/guest.rs` (`Guest { kind: Wsl|Lima, name }`, `Guest::script`), which `setup::wsl` and `setup::lima` share.
- `src/wsl.rs` (`wsl status [--json]`, `wsl compact [--distro] [--clean] [--yes]`): registry view of the distributions, `ext4.vhdx` sizes, `df` and build-output sizes of recorded clones; compaction deletes only directories named `target`, `artifacts` or `artifacts-temp` under recorded clones, runs `fstrim`, asks before `wsl --shutdown`, and compacts in one elevated PowerShell (`-EncodedCommand`, the disk path passed as base64 data, `Optimize-VHD` with a `diskpart` fallback that always detaches, exit code from `diskpart`). It never enables sparse disks. Verified on the development machine (2026-10-08, see `docs/manual-verification.md`): end-to-end `setup --wsl --web --clone`, `wsl status`, and a real `wsl compact --clean --yes` (build output removed, `fstrim`, one UAC prompt, vhdx 204.8 GiB to 204.3 GiB). The macOS and iOS sets are proven only by CI (base and web) and unit tests; the Mac session in `HANDOFF.md` closes the rest.
- `setup/lima.rs` (`setup --lima [--clone [<dir>]] [--vm-*]`, macOS only; epic `rayx-cli-guests`): macOS >= 13, Homebrew present (else `run rayx setup first`), Lima >= 2 (`brew install lima`, an older one is asked about, `brew upgrade lima`), `limactl list --json` (one object per line), then only for the instance `rayx`: `limactl create --tty=false --name=rayx --vm-type=vz --cpus --memory --disk --mount-only=<home>[:w] --containerd=none template:ubuntu-<pin>` once, `limactl start` when not running, then the guest layer. A clone that cannot succeed (no checkout, outside the home, unsafe target) is refused before anything is installed. `limactl` gets Homebrew's bin first on PATH while it is not on PATH yet.
- Lima sizing and records (epic `rayx-cli-guests`): `lima/sizing.rs` caps the defaults (6 CPUs, 12 GiB, 100 GiB) to `max(1, ncpu-2)` CPUs and `max(2, RAM/2)` GiB (from `sysctl -n hw.ncpu hw.memsize`, `df -k` on the Lima home), refuses explicit flags outside the limits before any limactl/brew command, needs >= 10 GiB free, and asks `Customize? [y/N]` once on creation through a `Prompter` (terminal, no `--yes`, not `--check`). `lima/edit.rs`: explicit `--vm-*` flags on the existing VM are an update (asked like an outdated requirement): `limactl stop` when running, `limactl edit --tty=false rayx <changed flags>`, `limactl start`; a smaller disk is refused. `setup/records.rs` writes `<config>/rayx/guests.json` (version 1: kind, name, ubuntu, flags union, clones, VM settings, retired) atomically after a real `--wsl`/`--lima` run (`record_outcome`; `--check` writes nothing); an unparsable or non-UTF-8 file is reported and left untouched. `src/doctor/guests.rs` joins the record with `limactl list --json` or the WSL registry and prints/JSONs `guests` with the `rayx lima|wsl remove <name>` hint for retired or missing ones.
- `setup --update` (epic `rayx-cli-guests`): every real `rayx setup` run (not `--check`, `--update`, `--wsl`, `--lima`) records its sets and project root in `<config>/rayx/setup.json` (`after_run`). `setup/update.rs` re-runs the recorded sets once per recorded root that still exists (a vanished root is reported and dropped), with that project's pins, or once without a project; a native host never gets `apt-get upgrade`. `setup/refresh.rs` then refreshes each current guest of the host's kind from `guests.json`: question `Update <kind> guest <name>?` (none with `--yes`; no terminal means not updated and exit 1), a stopped Lima VM is started and stopped again, Ubuntu older than the pin is reported outdated (migration replaces it), Linux rayx, `sudo apt-get update && sudo apt-get upgrade [-y]` and `rayx setup --update [--yes]` inside; a failing guest does not stop the next; `--check` inspects only running guests. An unparsable setup.json or guests.json is an error (exit 1), never `nothing recorded`. `rayx self update [--yes]` (`update.rs`, `Refresher`) offers the refresh after an install when a record exists and runs the executable captured before the install.
- Migration and removal (epic `rayx-cli-guests`, `setup/migrate.rs`, `setup/remove.rs`): a guest older than the pin is never upgraded in place. Lima: stop, `limactl rename rayx rayx-<old>` (the record is rewritten at once: renamed, retired, `migrating`; the rename is undone when the record cannot be written, and the record is probed before anything is stopped), then a new `rayx` from `template:ubuntu-<pin>` with the old VM's CPUs/memory/disk/home mount, Linux rayx, recorded clones re-cloned from their host sources, `rayx setup <recorded flags>` per clone, recorded current (`migrating` cleared). A rerun resumes (`pending_lima`: a retired `migrating` VM and no current `rayx`; `--check` only prints). WSL: `wsl --install -d Ubuntu-<pin>` next to the old distribution, the old entry is retired once the new one is set up. Reached from `setup --lima`, `setup --wsl` (live VERSION_ID) and `setup --update`; asked as `Create <new> with Ubuntu <pin> next to <old>?`; dirty clones (uncommitted or commits on no remote) are listed first. `rayx lima remove <name>` (`limactl delete --force`) and `rayx wsl remove <name>` (`wsl --unregister`) work only for recorded guests of the right OS, always ask unless `--yes` (no terminal refuses) and drop the record entry afterwards.
- Integration rules proven by the epic's advisory review (`rayx-cli-guests`, sprint s7): explicit `--vm-*` flags with a migration size the NEW VM (the old VM, running or recorded older, is never edited; a smaller disk is fine for a new VM); a guest rayx created is recorded even when the first run fails afterwards (`record_failed_first_run`, lima and wsl); a failing `limactl list` is `cannot read Lima` (`list_instances_strict`), never a missing guest, in refresh, remove and doctor (`unknown`); `--check` neither prompts nor starts anything (`wsl_is_running` first); only a missing record file is empty, anything unreadable is `RecordError::Unreadable` and left untouched; record temp files are unique per write.
- Open follow-ups of epic `rayx-cli-guests` (closed done-with-deferrals, 2026-10-14): (1) MAN-4, deferred by the owner: after the first release that contains the epic, run the two release rows of `docs/manual-verification.md` (`rayx self update` from the previous release on the Mac and on Windows must offer the refresh; `--yes` unattended) and record the result. (2) Observations from the final review, not defects of a criterion: `rayx doctor` calls a guest newer than the pin `outdated`; a migration that fails after creating the new VM shows only the retired VM in doctor until a rerun finishes; a stopped, unrecorded older `rayx` VM given `--vm-*` flags is edited before its Ubuntu is read; apt inside a guest could run non-interactively with `DEBIAN_FRONTEND=noninteractive` under `--yes`.
